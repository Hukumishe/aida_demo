# Анализ нагрузки и рекомендации по хостингу

## Обзор

Данный документ содержит полный анализ кода, оценку нагрузки для 400-500 активных пользователей и рекомендации по выбору хостинга.

## Технический стек

- **Backend**: NestJS (Node.js 20, TypeScript)
- **Database**: PostgreSQL (Prisma ORM)
- **Authentication**: JWT (Access + Refresh tokens)
- **File Storage**: Локальное хранилище (uploads/)
- **API**: RESTful API с Swagger документацией

## Архитектура приложения

### Основные модули:
1. **Authentication** - JWT аутентификация
2. **Studios** - Управление студиями
3. **Users/Staff** - Управление персоналом
4. **Clients** - Управление клиентами
5. **Services** - Управление услугами
6. **Schedule** - Расписание работы
7. **Busy Slots** - Занятые слоты
8. **Appointments** - Записи на прием
9. **Dashboard** - Статистика и аналитика
10. **Upload** - Загрузка файлов (аватары, портфолио)

## Анализ API endpoints

### Высокочастотные endpoints (используются ежедневно):

#### 1. Authentication (3 endpoints)
- `POST /auth/login` - Вход в систему
- `POST /auth/refresh` - Обновление токена
- `GET /auth/me` - Получение информации о пользователе

**Оценка частоты:**
- Login: 1-2 раза в день на пользователя = 400-1000 запросов/день
- Refresh: 10-20 раз в день на пользователя = 4000-10000 запросов/день
- Get me: 5-10 раз в день на пользователя = 2000-5000 запросов/день

**Нагрузка на БД:**
- Login: 1 SELECT запрос (users) + 1 UPDATE (последний вход, опционально)
- Refresh: 1 SELECT запрос (users)
- Get me: 1 SELECT запрос (users + staffProfile)

#### 2. Appointments (6 endpoints)
- `GET /studios/:studioId/appointments?date=YYYY-MM-DD` - Получение записей
- `POST /studios/:studioId/appointments` - Создание записи
- `PATCH /appointments/:id` - Обновление записи
- `POST /appointments/:id/no-show` - Отметка "не пришёл"
- `POST /appointments/:id/arrived` - Отметка "пришёл"
- `POST /appointments/:id/done` - Завершение записи

**Оценка частоты:**
- GET appointments: 10-20 раз в день на пользователя = 4000-10000 запросов/день
- POST appointments: 2-5 раз в день на пользователя = 800-2500 запросов/день
- PATCH appointments: 1-3 раза в день = 400-1500 запросов/день
- POST no-show/arrived/done: 5-10 раз в день = 2000-5000 запросов/день

**Нагрузка на БД:**
- GET appointments: 1 SELECT с JOIN (appointments, staff, client, service, arrivedByUser) + проверка доступности
- POST appointments: 1 SELECT (studio) + 1 SELECT (staff) + 1 SELECT (client) + 1 SELECT (service) + 1 SELECT (staffServiceOverride) + проверка доступности (несколько SELECT для busy slots и других appointments) + 1 INSERT
- PATCH appointments: 1 SELECT + проверка доступности + 1 UPDATE
- POST no-show/arrived/done: 1 SELECT + 1 UPDATE/DELETE (для no-show может быть INSERT в noShowIncome)

#### 3. Dashboard (2 endpoints)
- `GET /studios/:studioId/dashboard` - Статистика студии
- `GET /dashboard/all` - Статистика всех студий (только OWNER)

**Оценка частоты:**
- Studio dashboard: 2-5 раз в день на пользователя = 800-2500 запросов/день
- All studios dashboard: 1-3 раза в день (только OWNER) = 1-3 запроса/день

**Нагрузка на БД:**
- Studio dashboard: 1 SELECT (appointments с JOIN) + 1 SELECT (noShowIncomes с JOIN) + агрегация в памяти
- All studios dashboard: 1 SELECT (studios) + N SELECT (appointments для каждой студии) + N SELECT (noShowIncomes) + агрегация

#### 4. Clients (5 endpoints)
- `GET /studios/:studioId/clients?q=` - Список клиентов
- `POST /studios/:studioId/clients` - Создание клиента
- `GET /clients/:id` - Детали клиента
- `PATCH /clients/:id` - Обновление клиента
- `GET /clients/:id/statistics` - Статистика клиента
- `GET /clients/:id/appointments` - Записи клиента

**Оценка частоты:**
- GET clients: 5-10 раз в день = 2000-5000 запросов/день
- POST clients: 1-3 раза в день = 400-1500 запросов/день
- GET client details: 3-5 раз в день = 1200-2500 запросов/день
- PATCH clients: 1-2 раза в день = 400-1000 запросов/день
- GET statistics/appointments: 2-3 раза в день = 800-1500 запросов/день

**Нагрузка на БД:**
- GET clients: 1 SELECT с фильтрацией (LIKE для поиска)
- POST clients: 1 SELECT (проверка уникальности) + 1 INSERT
- GET client details: 1 SELECT
- PATCH clients: 1 SELECT + 1 UPDATE
- GET statistics: 1 SELECT (appointments с агрегацией)
- GET appointments: 1 SELECT (appointments с фильтрацией)

#### 5. Schedule (4 endpoints)
- `GET /studios/:studioId/schedule?date=YYYY-MM-DD` - Получение расписания
- `POST /studios/:studioId/schedule` - Создание/обновление дня расписания
- `POST /studios/:studioId/schedule/generate` - Генерация расписания
- `PATCH /schedule/day/:id` - Обновление дня расписания

**Оценка частоты:**
- GET schedule: 5-10 раз в день = 2000-5000 запросов/день
- POST/PATCH schedule: 1-2 раза в день = 400-1000 запросов/день
- POST generate: 1-2 раза в неделю = ~50 запросов/день

**Нагрузка на БД:**
- GET schedule: 1 SELECT (workScheduleDays с JOIN)
- POST schedule: 1 SELECT (проверка) + 1 INSERT/UPDATE (upsert)
- POST generate: Множественные INSERT (до 30 дней * количество сотрудников)
- PATCH schedule: 1 SELECT + 1 UPDATE

#### 6. Busy Slots (4 endpoints)
- `GET /studios/:studioId/busy-slots?date=YYYY-MM-DD` - Получение занятых слотов
- `POST /studios/:studioId/busy-slots` - Создание занятого слота
- `PATCH /busy-slots/:id` - Обновление слота
- `DELETE /busy-slots/:id` - Удаление слота

**Оценка частоты:**
- GET busy-slots: 5-10 раз в день = 2000-5000 запросов/день
- POST/PATCH/DELETE: 1-3 раза в день = 400-1500 запросов/день

**Нагрузка на БД:**
- GET busy-slots: 1 SELECT с фильтрацией по дате
- POST busy-slots: Проверка доступности + 1 INSERT
- PATCH busy-slots: 1 SELECT + проверка доступности + 1 UPDATE
- DELETE busy-slots: 1 DELETE

#### 7. Services (3 endpoints)
- `GET /studios/:studioId/services` - Список услуг
- `POST /studios/:studioId/services` - Создание услуги
- `PATCH /studios/:studioId/services/:id` - Обновление услуги

**Оценка частоты:**
- GET services: 3-5 раз в день = 1200-2500 запросов/день
- POST/PATCH services: 0.1-0.5 раз в день = 40-250 запросов/день

**Нагрузка на БД:**
- GET services: 1 SELECT
- POST services: 1 INSERT
- PATCH services: 1 SELECT + 1 UPDATE

#### 8. Staff (10+ endpoints)
- `GET /studios/:studioId/staff` - Список сотрудников
- `POST /studios/:studioId/staff` - Создание сотрудника
- `PATCH /staff/:userId` - Обновление сотрудника
- `GET /staff/:userId/profile` - Профиль сотрудника
- И другие...

**Оценка частоты:**
- GET staff: 2-5 раз в день = 800-2500 запросов/день
- POST/PATCH staff: 0.1-0.3 раза в день = 40-150 запросов/день

**Нагрузка на БД:**
- GET staff: 1 SELECT с JOIN (users + staffProfile)
- POST staff: 1 INSERT (users) + 1 INSERT (staffProfile)
- PATCH staff: 1 SELECT + 1 UPDATE

#### 9. Upload (2 endpoints)
- `POST /upload/avatar` - Загрузка аватара
- `POST /upload/portfolio` - Загрузка фото портфолио

**Оценка частоты:**
- Upload: 0.1-0.5 раз в день на пользователя = 40-250 запросов/день

**Нагрузка:**
- Загрузка файлов: Обработка файлов в памяти (до 10MB) + запись на диск + опционально UPDATE в БД

## Нагрузка на базу данных

### Количество запросов к БД в месяц:

Каждый HTTP запрос генерирует от 1 до 10+ SQL запросов (в зависимости от endpoint):

- **Простой GET** (например, список услуг): 1-2 SQL запроса
- **GET с JOIN** (например, appointments): 2-5 SQL запросов
- **POST с проверками** (например, создание записи): 5-15 SQL запросов
- **Dashboard** (агрегация): 2-10 SQL запросов + обработка в памяти

**Средний коэффициент**: 3-5 SQL запросов на 1 HTTP запрос

### SQL запросов в месяц:
- **Минимум**: 1,350,000 SQL запросов/месяц
- **Максимум**: 5,500,000 SQL запросов/месяц
- **Среднее**: ~3,100,000 SQL запросов/месяц

### SQL запросов в день:
- **Минимум**: ~61,000 SQL запросов/день
- **Максимум**: ~250,000 SQL запросов/день
- **Среднее**: ~141,000 SQL запросов/день

### SQL запросов в секунду:
- **Минимум**: ~0.7 QPS
- **Максимум**: ~2.9 QPS
- **Среднее**: ~1.6 QPS
- **Пиковая нагрузка**: ~5-8 QPS

## Нагрузка на сервер

### CPU:
- **Средняя нагрузка**: 10-20% (1 ядро)
- **Пиковая нагрузка**: 30-50% (1 ядро)
- **Рекомендуется**: 2 ядра для комфортной работы

### RAM:
- **Node.js процесс**: 200-400 MB (в зависимости от количества соединений)
- **PostgreSQL**: 100-200 MB (для небольшой БД)
- **Система**: 100-200 MB
- **Итого**: 400-800 MB
- **Рекомендуется**: 1-2 GB RAM (с запасом)

### Диск:
- **Приложение**: ~100-200 MB (node_modules + код)
- **База данных**: 100-500 MB (начальный размер)
- **Логи**: 100-500 MB/месяц (если включено)
- **Загруженные файлы**: 100 MB - 1 GB (в зависимости от использования)
- **Итого**: 400 MB - 2 GB
- **Рекомендуется**: 10-20 GB (с запасом для роста)

### Сетевая нагрузка:
- **Входящий трафик**: ~50-100 MB/день = ~1-2 GB/месяц
- **Исходящий трафик**: ~200-500 MB/день = ~4-10 GB/месяц
- **Итого**: ~5-12 GB/месяц

## Рекомендации по оптимизации

### 1. Кэширование:
- Использовать Redis для кэширования часто запрашиваемых данных:
  - Список услуг
  - Список сотрудников
  - Расписание (на день)
- Снизит нагрузку на БД на 20-30%

### 2. Индексы БД:
- Убедиться, что все индексы из Prisma schema созданы
- Добавить составные индексы для частых запросов:
  - `(studioId, startAt)` для appointments
  - `(studioId, date)` для schedule
  - `(studioId, phone)` для clients

### 3. Connection Pooling:
- Настроить connection pooling для PostgreSQL:
  - Минимум: 5 соединений
  - Максимум: 20 соединений
  - Это снизит нагрузку на БД

### 4. Логирование:
- Отключить или ограничить логирование в production
- Использовать ротацию логов
- Хранить логи не более 30 дней

### 5. File Storage:
- Рассмотреть использование внешнего хранилища:
  - AWS S3
  - Google Cloud Storage
  - Cloudflare R2
- Это снизит нагрузку на сервер и улучшит производительность

### 6. CDN:
- Использовать CDN для статических файлов (uploads/)
- Cloudflare (бесплатный тариф)
- Это снизит нагрузку на сервер

### 7. Rate Limiting:
- Добавить rate limiting для API:
  - 100 запросов/минуту на пользователя
  - 1000 запросов/час на IP
- Защита от злоупотреблений

- **Рекомендуемая конфигурация**: 2-4 CPU, 4 GB RAM, 40 GB SSD ($20-40/месяц)

При правильной оптимизации (кэширование, индексы, connection pooling) нагрузка будет распределена равномерно, и приложение будет работать стабильно даже при пиковых нагрузках.
