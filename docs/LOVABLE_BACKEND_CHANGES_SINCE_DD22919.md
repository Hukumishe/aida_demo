# Промпт для Lovable: изменения бэкенда относительно коммита `dd22919`

Скопируйте блок **«Промпт для Lovable»** ниже целиком в чат Lovable (или добавьте в системный контекст фронтенда).

**Базовая версия бэкенда в сравнении:** коммит `dd22919` — *«feat(referral-links): studio marketing links, source field, cashback accumulation»* (реферальные маркетинговые ссылки, поле источника, накопление кэшбэка).

**Текущая целевая версия:** ветка `main` после внедрения **организационного слоя (multi-tenant)** и правок **клиентской лояльности по организации**, а не по студии.

Подробный сценарий интеграции (роли, `/organizations`, `/studios`, env) см. в `**LOVABLE_ORGANIZATION_INTEGRATION_PROMPT.md`** — здесь только **дельта относительно `dd22919`**.

---

## Промпт для Lovable

### 1) Модель данных и «владелец» сущностей

**В `dd22919`** сеть и тенантность в API в основном опирались на **филиал (`studioId`)**; реферальные ссылки и клиентская логика развивались в этом контексте.

**Сейчас** введена сущность `**Organization`** (организация / сеть). У клиентов, пользователей, складов, настроек лояльности и др. есть `**organizationId**`. Филиал (`**Studio**`) принадлежит организации. Фронтенд должен считать **организацию источником истины** для: общей базы клиентов, уникальности телефона, кастомной лояльности (CUSTOM), многих маркетинговых и складских правил.

**Что сделать в UI:** после логина опираться на `**GET /auth/me` → `user.organizationId`**, `**user.studioId**`, `**user.role**`; для выбора филиала — `**GET /studios**` (и не хардкодить id).

---

### 2) Авторизация и роли (дельта)

**Появилось по сравнению с `dd22919`:**

- В payload JWT / `**/auth/me`** — поля `**organizationId**`, при необходимости вложенное `**organization**`.
- Роль `**DEVELOPER**` — доступ ко **всем** организациям и филиалам; эндпоинты `**GET/POST /organizations`** (создание и список организаций) — только для этой роли.
- Остальные роли ограничены своей организацией и/или филиалом (как описано в `LOVABLE_ORGANIZATION_INTEGRATION_PROMPT.md`).

**Что сделать в UI:** если в коде после `dd22919` предполагался только «один салон без явной организации», добавить хранение `**organizationId`** и сценарий для `**DEVELOPER**` (список организаций + создание филиала с `**organizationId**`).

---

### 3) Филиалы `POST /studios` (дельта)

**Сейчас** при создании филиала для `**DEVELOPER`** в теле можно передать `**organizationId**`, чтобы привязать студию к нужной организации. Для владельца сети филиал по-прежнему создаётся в организации пользователя без обязательного поля.

**Что сделать в UI:** форма «добавить филиал» для платформенной роли должна позволять выбрать организацию и отправить `**organizationId`**.

---

### 4) Клиенты CRM: телефон и организация

**Отличие от `dd22919`:** уникальность телефона — **в пределах `organizationId`**, а не глобально по всей базе.

**Что сделать в UI:** сообщения об ошибке дублирования телефона формулировать как «клиент с таким номером уже есть в **этой сети**», не «в системе» без уточнения.

---

### 5) Карточка клиента `GET /studios/:studioId/clients/:id` — лояльность и рефералка

**В `dd22919`** логика деталей клиента могла подразумевать привязку части данных (в т.ч. кастомной лояльности) к **контексту студии** (в т.ч. через query-параметры).

**Сейчас:**

- Реферальные флаги первого визита и блок **CUSTOM-лояльности** считаются по `**client.organizationId`**, а не по выбранному филиалу.
- Опциональный query `**?studioId=...**` для `**GET .../clients/:id**` помечен как **устаревший** — **не влияет** на лояльность и рефералку; оставлен для обратной совместимости старых ссылок.
- В теле ответа:
  - `**organizationLoyalty`** — основной объект кастомной лояльности (режим CUSTOM у **организации**): внутри, в частности, `**organizationId`**, `**totalPaid**`, `**currentTier**`, `**milestones**`, `**nextStep**`.
  - `**studioLoyalty**` — **устаревший алиас** того же объекта (для старых экранов); новый код должен читать `**organizationLoyalty`**.

**Что сделать в UI:**

- Перейти на отображение `**organizationLoyalty`**; не завязывать подписи на «студия», если речь про сетевую лояльность — это **организация клиента**.
- Убрать зависимость от передачи `studioId` в query для корректности лояльности (она больше не нужна).

---

### 6) `PATCH /studios/:studioId/clients/:id` — ручная кастомная лояльность

**Отличие от `dd22919`:** для смены ручного уровня / сброса в CUSTOM-режиме предпочтительно тело с:

- `**customLoyaltyOrganizationId`** — должен **совпадать** с `**organizationId` клиента**;
- опционально устаревшее `**customLoyaltyStudioId`** — сервер сам переводит в `organizationId` студии; если указаны оба и они противоречат друг другу — будет **400**.

По-прежнему используются `**customLoyaltyTierId`**, `**customLoyaltyClearManual**` (только для ролей уровня owner — как на бэкенде).

**Что сделать в UI:** в формах редактирования кастомного уровня подставлять `**user.organizationId` клиента** (или `client.organizationId` из карточки), а не id выбранного филиала.

---

### 8) Реферальные ссылки (модуль с `dd22919`)

Функциональность `**referral-links`** из `dd22919` сохраняется, но данные и проверки доступа согласованы с **организационным** контуром (как на бэкенде в сервисе ссылок). Не смешивайте в одном UI списки ссылок разных организаций без явного фильтра.

---

## Чеклист обновления фронтенда (кратко)

1. `**/auth/me`:** хранить `**organizationId`**, `**role**`, `**studioId**`.
2. **Список филиалов:** `GET /studios`; для `**DEVELOPER`** — показывать принадлежность к организации, если поле есть в ответе.
3. **Карточка клиента:** использовать `**organizationLoyalty`**; не полагаться на `**?studioId**` для лояльности.
4. **PATCH клиента (CUSTOM loyalty):** `**customLoyaltyOrganizationId`** = организация клиента; отказ от UX «выбери студию для лояльности».
5. **Nextbot raw client:** читать лояльность из `**organizationLoyalty`**.

---

## Конец промпта

Используйте базовый URL API из переменных окружения и `**Authorization: Bearer**`. Стилистика UI — по проекту Lovable; контракты — строго по текущему OpenAPI/Swagger бэкенда при расхожденях с устаревшими экранами, сделанными под `**dd22919**`.
