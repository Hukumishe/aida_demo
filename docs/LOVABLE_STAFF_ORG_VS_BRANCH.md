# Промпт для Lovable: вкладка «Сотрудники» — филиал и административный персонал

Скопируйте блок **«Промпт»** ниже целиком в чат Lovable.

---

## Промпт

### Модель ролей (уровень организации vs филиала)

В системе часть ролей работает **на уровне организации (сети)** и **не привязана к конкретному филиалу** (`studioId` может быть пустым / null в профиле пользователя): это **заместитель владельца** (`DEPUTY_OWNER`) и **менеджер** (`MANAGER`) в смысле сетевого управления. Они видят **все филиалы** своей организации; объём действий ограничивается правами роли (как в остальном приложении).

Остальные роли в основном привязаны к филиалу: например **администратор филиала** (`ADMIN`) и **мастер** (`MASTER`) — контекст выбранного филиала.

**Владелец** (`OWNER`) и **SERVICE** тоже обычно рассматриваются как уровень сети (полный доступ по организации в рамках продуктовых правил).

### Задача UI: вкладка «Сотрудники»

Сделай экран **«Сотрудники»** с **двумя явными разделами** (две секции, аккордеон или подвкладки):

1. **Сотрудники филиала**  
   Список людей, относящихся к **текущему выбранному филиалу** (`studioId` выбранного филиала): в первую очередь **ADMIN**, **MASTER**, а также менеджеры/другие роли, если у них в данных привязка именно к этому филиалу.

2. **Административный персонал (сеть)**  
   Список пользователей **организации**, которые **не привязаны к одному филиалу** или по продуктовым правилам относятся к **сетевому** уровню: их нужно показывать **одинаково при переключении любого филиала** (не дублировать логику «только в этом филиале»).

Визуально:

- Заголовки разделов на русском: например **«Филиал»** и **«Администрирование сети»** (или аналогично по тону приложения).
- В карточке сотрудника: ФИО, роль, филиал (если есть), контакты — как в остальном UI.
- При смене филиала в шапке: **блок «Административный персонал» не меняется по составу** (или меняется только если бэкенд отдаёт объединённый список — см. ниже); **блок «Филиал»** обновляется под выбранный `studioId`.

### Данные с бэкенда

- **Сотрудники филиала:** **`GET /studios/:studioId/staff`** — пользователи с привязкой к этому филиалу (`studioId` = выбранный филиал).
- **Административный персонал сети:** **`GET /studios/:studioId/staff/network`** — пользователи организации этого филиала с **`studioId = null`** и ролями `OWNER`, `DEPUTY_OWNER`, `SERVICE`, `MANAGER`. Список **не зависит** от выбранного филиала (одинаковый для всех филиалов сети); `studioId` в пути нужен только для проверки доступа и определения `organizationId`.

Оба запроса с тем же **`Authorization: Bearer`** и контекстом, что и остальные вызовы по филиалу.

При **`POST /studios/:studioId/staff`** для ролей **MANAGER**, **OWNER**, **DEPUTY_OWNER**, **SERVICE** бэкенд сохраняет **`studioId = null`** (сеть), организация берётся из филиала в пути. **ADMIN** и **MASTER** остаются привязанными к этому филиалу.

### Права

- Пользователи **уровня сети** (OWNER, DEPUTY_OWNER, MANAGER в смысле сети, SERVICE, DEVELOPER по правилам проекта) должны видеть **оба** раздела там, где это разрешено продуктом.
- Пользователи **только филиала** (например ADMIN/MASTER без сетевого доступа) — только раздел **«Филиал»** (и редирект/скрытие сетевого блока, если так решено в продукте).
