# Промпт для Lovable: недавние изменения бэкенда (сводный)

Скопируйте блок **«Промпт»** ниже целиком в чат Lovable. Подробности по отдельным темам:  
`LOVABLE_ORGANIZATION_INTEGRATION_PROMPT.md`, `LOVABLE_BACKEND_CHANGES_SINCE_DD22919.md`, `LOVABLE_DEVELOPER_SCREEN.md`, `LOVABLE_STUDIO_SERVICE_OFFERING.md`.

---

## Промпт

### Общий контекст

Бэкенд AIDA (NestJS): мультиарендность по **организациям**, филиалы `**studioId`**, Bearer-токен. Базовый URL из env. Детали интеграции — в `LOVABLE_ORGANIZATION_INTEGRATION_PROMPT.md`.

---

### 1) Услуги: активность по филиалу

Каталог услуг общий для **организации**, но услугу можно **скрыть только в одном филиале**, не выключая её в сети.

- `**GET /studios/:studioId/services`** — у каждой услуги есть `**isOfferedInStudio**` (можно ли записывать/показывать в **этом** филиале).
- `**PATCH /studios/:studioId/services/:id`** — поле `**isActive**` = отключить услугу **во всей организации**.
- `**PATCH /studios/:studioId/services/:id/studio-offering`** — тело `**{ "offered": true | false }**`: включить/выключить **только в текущем филиале**.

В UI: два уровня — «в каталоге сети» (`isActive`) и «в этом филиале» (`isOfferedInStudio` / переключатель на `studio-offering`). Не смешивай смысл с глобальным `isActive`.

---

### 2) Клиенты: лояльность по организации

- В карточке клиента используй `**organizationLoyalty`** для кастомной лояльности (режим CUSTOM). Поле `**studioLoyalty**` — устаревший алиас того же объекта.
- Ручное изменение кастомного уровня: в `**PATCH .../clients/:id**` передавай `**customLoyaltyOrganizationId**` (= `organizationId` клиента), опционально устаревший `**customLoyaltyStudioId**` (сервер сам переведёт в организацию).
- Query `**?studioId**` у `**GET .../clients/:id**` устарел и **не влияет** на лояльность — не опирайся на него.

---

### 3) Роль DEVELOPER ≈ владелец в сети

Для **бизнес-экранов** (не только `/organizations`) пользователь с ролью `**DEVELOPER`** должен иметь те же возможности, что **OWNER / DEPUTY_OWNER / SERVICE** внутри выбранной сети: дашборд, склад, лендинг, промпты, задачи, реферальные ссылки, чёрный список и т.д. **Переключатель филиала** для DEVELOPER — по всему списку из `**GET /studios`**, не только `user.studioId`.

Отдельно только у DEVELOPER: **раздел «Организации»** — `GET/POST /organizations`, создание филиала с `**organizationId`** в теле `POST /studios` при необходимости.

Обнови навигацию и проверки ролей на фронте: не скрывай пункты уровня владельца от DEVELOPER (если они скрывались только для «не owner»).

---

### 4) Промпты и задачи (уточнение API)

- `**/prompts**` (CRUD промптов): доступ у **уровня владельца** и **SERVICE**, а также **DEVELOPER** — ориентируйся на ответ **403** и роль из `**/auth/me`**, не хардкодь только SERVICE.
- В **задачах** поле «контролёры» может включать пользователей с ролями **OWNER / DEPUTY_OWNER / SERVICE** (не только менеджеров/админов), если выбираешь пользователей филиала по списку ролей.

---

### 5) Ошибки

**403** — чаще всего неверный контекст филиала/организации или роль; не ретраить без смены контекста.
