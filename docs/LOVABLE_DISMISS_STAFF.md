# Увольнение сотрудника вместо удаления — промпт для Lovable

## Что изменилось на бэкенде

Сотрудники **больше не удаляются**, а **увольняются**. Данные сохраняются, доступ отключается.

- При «увольнении» вызывается тот же эндпоинт **DELETE** (семантика «убрать из активных»).
- Пользователь в БД остаётся: выставляется **`isActive: false`**. Профиль, расписание, записи и прочие связи **не удаляются**.
- После увольнения сотрудник **не может войти** (логин и refresh возвращают ошибку для неактивных пользователей).

---

## API (без изменений URL)

**DELETE** `/studios/:studioId/staff/:userId`  
(или **DELETE** `/staff/:userId` в зависимости от вашего базового пути)

**Заголовки:** `Authorization: Bearer <access_token>`

### Ответ 200 (успешное увольнение)

Тело ответа — **обновлённый пользователь** (как при PATCH), а не удалённая запись:

```json
{
  "id": "user-uuid",
  "email": "user@example.com",
  "phone": "+79991234567",
  "role": "MASTER",
  "studioId": "studio-uuid",
  "isActive": false,
  "createdAt": "...",
  "updatedAt": "...",
  "staffProfile": {
    "firstName": "Иван",
    "lastName": "Петров",
    ...
  }
}
```

Важно: **`isActive`** в ответе будет **`false`**.

### Ответ 400

- **"User is already dismissed"** — сотрудник уже уволен, повторное увольнение невозможно.
- **"Cannot dismiss OWNER role"** / **"Cannot dismiss DEPUTY_OWNER role"** — ограничения по ролям (как раньше при удалении).

### Ответ 403 / 404

Без изменений (нет прав или пользователь не найден).

## Что сделать во фронте (Lovable)

1. **Текст и смысл действия**
   - Вместо кнопки/действия **«Удалить»** использовать **«Уволить»** (или «Снять с доступа»).
   - В диалоге подтверждения писать, что сотрудник будет **уволен**, доступ отключится, **данные сохраняются** (история, записи и т.д. останутся).

2. **После успешного увольнения**
   - Не удалять карточку сотрудника из списка: запрос возвращает пользователя с `isActive: false`.
   - Обновить состояние: подставить в список обновлённого пользователя (с `isActive: false`) или перезапросить список сотрудников.
   - Показывать у уволенных статус, например: **«Уволен»** (бейдж/подпись), серый стиль строки или иконка.

3. **Список сотрудников**
   - В ответах API у каждого пользователя есть поле **`isActive`**.
   - Отображать и активных (`isActive: true`), и уволенных (`isActive: false`), чтобы данные сохранялись и были видны.
   - Для уволенных: не давать выбирать в «активных» действиях (например, при создании записи выбирать только активных; при необходимости фильтровать по `isActive === true` на фронте или по отдельному запросу, если бэкенд начнёт отдавать только активных).

4. **Ошибки**
   - При **400** и тексте **"User is already dismissed"** показывать сообщение вида: «Сотрудник уже уволен».
   - Остальные 400/403/404 обрабатывать как раньше.

5. **Поведение при повторном нажатии**
   - Для пользователя с `isActive: false` кнопку «Уволить» можно скрыть или сделать неактивной, чтобы не вызывать лишний запрос.

## Краткий чеклист

- [ ] Заменить «Удалить» на «Уволить» в кнопках и диалогах.
- [ ] В подтверждении указать, что данные сохраняются, отключается только доступ.
- [ ] После 200 не удалять карточку из списка; обновить данные (в т.ч. `isActive: false`).
- [ ] В списке сотрудников показывать статус «Уволен» для записей с `isActive: false`.
- [ ] Обработать 400 «User is already dismissed».
- [ ] Для уволенных не показывать/не разрешать действие «Уволить» повторно.
