# Архитектура услуг: Service, StaffService, StaffServiceOverride

## Зачем нужны три уровня?

Система использует **трехуровневую архитектуру** для гибкого управления услугами:

### 1. **Service** (services) - Каталог услуг студии
**Что это:** Общий список услуг, которые предоставляет студия

**Пример:**
```
- Стрижка (60 мин, 3000₸)
- Окрашивание (120 мин, 5000₸)
- Маникюр (90 мин, 2500₸)
```

**Назначение:**
- Централизованное управление услугами студии
- Общие настройки по умолчанию (время, цена)
- Можно включить/выключить услугу для всей студии

**Аналогия:** Это как меню ресторана - список всех блюд, которые ресторан готовит.

---

### 2. **StaffService** (staff_services) - Кто что умеет делать
**Что это:** Связь между сотрудниками и услугами (many-to-many)

**Пример:**
```
Мастер Иван:
  ✓ Стрижка
  ✓ Окрашивание
  ✗ Маникюр

Мастер Мария:
  ✗ Стрижка
  ✗ Окрашивание
  ✓ Маникюр
```

**Назначение:**
- Показывает, какие услуги может оказывать каждый сотрудник
- Не все мастера умеют делать все услуги
- Можно назначить услугу сотруднику или убрать

**Аналогия:** Это как список навыков каждого повара - кто что умеет готовить.

**Важно:** Без этой связи сотрудник не может оказывать услугу, даже если она есть в каталоге студии.

---

### 3. **StaffServiceOverride** (staff_service_overrides) - Индивидуальные настройки
**Что это:** Кастомные настройки времени и цены для конкретного сотрудника и услуги

**Пример:**
```
Услуга "Стрижка" (по умолчанию: 60 мин, 3000₸)

Мастер Иван:
  - Кастомное время: 90 мин (делает дольше)
  - Кастомная цена: 5000₸ (берёт дороже)

Мастер Мария:
  - Использует настройки по умолчанию (60 мин, 3000₸)
```

**Назначение:**
- Позволяет установить индивидуальное время для каждого мастера
- Позволяет установить индивидуальную цену для каждого мастера
- Можно временно отключить кастомные настройки

**Аналогия:** Это как индивидуальные рецепты или порции - один повар готовит блюдо быстрее, другой медленнее, но качество одинаковое.

**Важно:** Override можно создать только для услуги, которая уже назначена сотруднику (через StaffService).

---

## Как это работает вместе

### Сценарий 1: Создание записи (Appointment)

```
1. Клиент выбирает услугу "Стрижка"
2. Система проверяет StaffService:
   - Может ли мастер Иван делать "Стрижку"?
   - Если нет → ошибка "Услуга не назначена сотруднику"
   
3. Если да, система проверяет StaffServiceOverride:
   - Есть ли кастомные настройки для (Иван + Стрижка)?
   - Если есть и isActive = true:
     → Используется override.durationMin (90 мин)
   - Если нет или isActive = false:
     → Используется service.defaultDurationMin (60 мин)
```

### Сценарий 2: Отображение услуг сотрудника

```
GET /staff/:staffUserId/services

Ответ включает:
- service: { name: "Стрижка", defaultDurationMin: 60, defaultPrice: 3000 }
- override: { durationMin: 90, price: 5000, isActive: true }

Frontend показывает:
"Стрижка: 90 мин (обычно 60 мин), 5000₸ (обычно 3000₸)"
```

## Почему не объединить в одну таблицу?

### ❌ Плохой вариант (всё в Service):

```sql
Service:
  - id
  - name
  - durationMin  -- Проблема: какое время? для кого?
  - price         -- Проблема: какая цена? для кого?
  - staffUserId   -- Проблема: один мастер или все?
```

**Проблемы:**
- Невозможно показать, какие услуги умеет делать каждый мастер
- Невозможно установить разное время для разных мастеров
- Придётся дублировать услугу для каждого мастера

### ✅ Хороший вариант (три таблицы):

**Разделение ответственности:**
- `Service` - что предлагает студия (один раз)
- `StaffService` - кто что умеет (связь)
- `StaffServiceOverride` - индивидуальные настройки (опционально)

**Преимущества:**
- ✅ Одна услуга в каталоге, но разные мастера могут её делать
- ✅ Можно установить разное время/цену для каждого мастера
- ✅ Можно временно отключить кастомные настройки
- ✅ Гибкость и масштабируемость

## Примеры использования

### Пример 1: Новый мастер

```
1. Создаём услугу "Стрижка" в Service (60 мин, 3000₸)
2. Назначаем услугу мастеру через StaffService
3. Мастер работает со стандартным временем (60 мин)

Результат: Мастер может делать стрижку за 60 минут
```

### Пример 2: Опытный мастер

```
1. Услуга "Стрижка" уже есть в Service (60 мин, 3000₸)
2. Услуга уже назначена мастеру через StaffService
3. Создаём StaffServiceOverride:
   - durationMin: 45 мин (делает быстрее)
   - price: 5000₸ (берёт дороже)
   - isActive: true

Результат: Мастер делает стрижку за 45 минут и берёт 5000₸
```

### Пример 3: Временное изменение

```
1. У мастера есть override (90 мин, 5000₸)
2. Мастер заболел, работает медленнее
3. Обновляем override:
   - durationMin: 120 мин
   - isActive: true

Результат: Время обновлено, но можно вернуть обратно
```

### Пример 4: Отключение кастомных настроек

```
1. У мастера есть override (90 мин, 5000₸)
2. Решаем использовать стандартные настройки
3. Обновляем override:
   - isActive: false

Результат: Используются стандартные настройки (60 мин, 3000₸)
   Но override остаётся в базе - можно включить обратно
```

## Структура данных

### Service (services)
```typescript
{
  id: "service-1",
  name: "Стрижка",
  defaultDurationMin: 60,    // Стандартное время
  defaultPrice: 3000,         // Стандартная цена
  isActive: true              // Активна ли услуга
}
```

### StaffService (staff_services)
```typescript
{
  id: "staff-service-1",
  staffUserId: "master-ivan",
  serviceId: "service-1"
}
// Просто связь: "Мастер Иван умеет делать Стрижку"
```

### StaffServiceOverride (staff_service_overrides)
```typescript
{
  id: "override-1",
  staffUserId: "master-ivan",
  serviceId: "service-1",
  durationMin: 90,            // Кастомное время
  price: 5000,                 // Кастомная цена
  isActive: true              // Использовать кастомные настройки?
}
```

## Итоговая схема

```
┌─────────────┐
│   Service   │  ← Каталог услуг студии
│  (Стрижка)  │     (что предлагает студия)
└──────┬──────┘
       │
       │ many-to-many
       │
       ▼
┌─────────────────┐
│  StaffService    │  ← Кто что умеет
│ (Иван + Стрижка)│     (навыки сотрудников)
└────────┬────────┘
         │
         │ optional (0 или 1)
         │
         ▼
┌──────────────────────┐
│ StaffServiceOverride │  ← Индивидуальные настройки
│ (Иван: 90 мин, 5000₸)│     (кастомное время/цена)
└──────────────────────┘
```

---

## Вывод

**Service** - это "что" (каталог услуг)
**StaffService** - это "кто" (навыки сотрудников)
**StaffServiceOverride** - это "как" (индивидуальные настройки)

Все три уровня нужны для гибкого управления услугами в студии, где:
- Не все мастера умеют делать все услуги
- Разные мастера могут работать с разной скоростью
- Разные мастера могут брать разную цену
- Нужна возможность временно менять настройки

Это стандартная архитектура для систем управления услугами с индивидуальными настройками.
